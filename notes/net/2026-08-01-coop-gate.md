# The co-op gate: two processes, one room, and the two defects it found on day one

`tools/coop.ps1` launches two real game clients against the live Supabase project,
puts them in one room, plays a run, and asserts on what each of them saw. It is the
only test in the repo that can be true or false about replication, and it found two
real defects in its first three runs.

**Run it after any change to `scripts/net/`.** It costs ~70 s and roughly 4000
Supabase events, against a free tier that allows two million a month.

---

## Why it is not in `--verify`

`session_runtime.gd`, `replication.gd` and `remote_player.gd` are the three files
that carry a co-op run, and **none of them can be true or false inside one process**:
what they do is move state across a wire into a second copy of the game.

The hole was measured, not suspected. An adversarial pass sabotaged **seven
constants across all three files** and `--verify` still printed
`=== 676 passed, 0 failed ===`.

A single-process test cannot close it. The best it can do is stand a fake channel
between the two halves and assert that the codec round trips through it — which is a
copy of the thing under test, and is exactly what CLAUDE.md means by "a test that
does not call what the game calls". So the gate is a second OS process, a real
channel, and the actual game on both ends.

Headless is correct here and is *not* the trap CLAUDE.md warns about: that warning is
`--shot`/`--frames` awaiting `frame_post_draw` with no rendering device, and nothing
in the co-op probe waits on a frame.

## What it asserts

Each line is a distinct wire path, in a distinct direction.

| Check | The path it proves |
| --- | --- |
| both clients were still in the run | neither died; see "the corpse" below |
| seeds agree | both machines built the same world |
| each sees exactly one peer | presence resolved on both ends |
| each peer was **posed** | a `me` crossed *and was applied* |
| each peer **moved** | successive `me`s were interpolated |
| the client built puppets | the host's `snap`/`spawn` arrived |
| the host applied claims | the client's `dmg` arrived |
| the client's puppets died | the host's `kill` came back |
| the client learned the forced round | `world` arrived and `_apply_round` ran |

The "posed" check is the sharp one. `_sync_roster` builds every avatar **hidden** and
only `_drive` reveals it, and only once it has a delivered pose — so a visible avatar
is proof a body message crossed the wire, which a roster count cannot claim.

## Every check has a control, and here they are

`pwsh tools/coop-controls.ps1` breaks one wire path at a time and requires the named
check to fail. Full sweep, 2026-08-01:

| Control | What it cuts | Verdict |
| --- | --- | --- |
| `seed-ignored` | the client uses its own seed | discriminates (1 failed) |
| `me-inert` | no body message is applied | discriminates (3 failed) |
| `me-frozen` | first pose lands, no later one does | discriminates (2 failed) |
| `snap-inert` | the host never describes its horde | discriminates (5 failed) |
| `claim-inert` | the client tells nobody about its hits | discriminates (1 failed) |
| `kill-inert` | the client ignores death confirmations | discriminates (1 failed) |
| `round-inert` | the round on the wire is discarded | discriminates (1 failed) |

`me-frozen` is the one worth reading: it fails **only** the two "moved" checks while
"posed" still passes, which is what makes those two separate assertions rather than
one restated twice.

Downstream failures are printed but not required — cutting one path legitimately
starves the ones below it. What is required is that the *named* check fails.

**The control harness needed its own correction.** Its first `me-frozen` anchor
resolved into `_apply_snap` rather than `_apply_me` — the two functions have an
identically-worded `samples` line at different indentation — so it froze *puppets*
while claiming to freeze *avatars*. `-DryRun` now prints the file and line every
anchor lands on, for exactly this reason.

## Defect 1: a refused `world` message was lost for the rest of the run

`_send_world` latched its change-detector **before** the send and discarded the
send's return value:

```gdscript
_world_sig = sig
_chan.send(REPL.EV_WORLD, ...)      # returns false when the budget is spent
```

`realtime.gd::send()` returns false when the second's `SEND_BUDGET` is spent. `world`
is the one message in the file with **no successor to carry its contents** — `snap`
supersedes itself, `kill` and `dmg` re-queue through `_keep` — so a refused frame was
simply gone: the next tick computed the same signature, matched the latch, and
returned.

Not bad luck, either. A round change is the busiest tick there is (spawns and kills
batch onto the same frame), and `tick()` sends `world` **last** — so the message that
cannot be recovered is structurally the first one the budget refuses.

Found because the host reported `dropped_sends: 1` and the client sat on round 1 for
fifteen seconds. Fixed by latching only on an accepted send.

## Defect 2 (in the probe, not the game): a dead client looks exactly like a dead network

The first version of the probe had the host stand still and never fire. That survived
round 1 and was eaten alive the moment the gate forced round 3 — which took
`Game.state` out of `STATE_PLAY`, so `main._process` stopped driving
`_session.tick()`, so **every outbound message on the host stopped at once** while the
probe (`PROCESS_MODE_ALWAYS`) kept happily sampling.

The symptom was a `world_sig` pinned at round 1 next to a `round_now` of 3, and it
read as a replication bug for two runs. Two things came out of it:

- Both bots now fight, and their HP is topped up every frame. What is under test is
  the wire, not whether a bot with a starting pistol can hold a corner at round 3.
  Tuning the round down until they happened to survive would have been a threshold
  that rots the first time the horde is rebalanced.
- **"both clients were still in the run at the end" is asserted first**, because it
  invalidates everything below it.

## The round assertion was decoration until the host was forced to change round

Both machines call `begin_run()` and both sit on round 1 for the whole budget, so
"they agree on the round" passed against a client that had never received a `world`
message. The probe now forces the host to round 3 at t=30 s, which makes the client's
round number reachable **only** through `_apply_round` — and `round-inert` proves it
fails when that path is cut.


88 shots to 22 applied claims is not a defect: the bot fires on a timer whether or
not the raycast finds a body, and a claim against an id the host has already killed
is counted as not landed. It is worth watching only if it goes to zero.

## What the gate still does not cover

- **The web export.** Both processes are the desktop binary. `WebSocketPeer` in the
  browser is verified by hand (see the probe note); the *replication* half has never
  run there.
- **More than two clients.** `MAX_PLAYERS` is 2 for event-budget reasons and the gate
  matches it.
- **Downs and revives, shared doors, the box, traps and the knife against puppets.**
  All deferred; see the topology decision note.
- **The heartbeat pulse.** Native builds never install it (`OS.has_feature("web")`),
  so nothing here exercises it.
